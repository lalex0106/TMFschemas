# 代码库审查与完善计划

## 1. 审查背景

当前仓库包含 TM Forum 早期版本的 JSON Schema 定义，主要服务于 Open API Catalog 的验证流程。随着官方发布基于 YAML 的新版 schema，我们需要在保留既有资产的基础上，构建企业级的数据 schema 管理与扩展机制。本计划记录对现有仓库的审查结果，并提出围绕新目标的总体完善方案。

## 3. 现有能力与不足

### 3.1 能力现状
- **Schema 资产**：大量符合 JSON Schema draft-07 的实体定义，可直接作为迁移和比对的基准。
- **验证工具**：`.circleci/validate.js` 使用 `jsonschema` 与 `$RefParser` 对 schema 进行一致性校验，并输出校验结果，适合作为未来 CI 的基础。
- **Node.js 环境**：`package.json` 中已引入 `js-yaml`、`jsonschema` 等依赖，为处理 YAML 与 JSON 提供基础能力。

### 3.2 不足之处
- **缺少 YAML 处理管线**：目前仅支持 JSON 文件，无法直接引入官方新版 YAML 规格。
- **无系统化的 Schema 版本管理**：缺乏对不同来源、不同版本 schema 的分层与追踪策略。
- **扩展性有限**：难以合并外部参考资料或企业自定义要求，缺少元数据与注释机制。
- **自动化薄弱**：缺少统一的构建/转换脚本、持续集成配置过时。

## 4. 面向新目标的完善方向

### 4.1 架构规划
1. **数据源分层管理**
   - `sources/tmf-official/`：同步官方 YAML 发布版本，保留原始文件。
   - `sources/external/`：存放其他行业标准或企业内部参考资料。
   - `overrides/enterprise/`：记录企业特定的差异与扩展描述。

2. **转换与合并流水线**
   - `tools/ingest`：负责拉取并解析 YAML，统一转换为中间格式（JSON Schema 草稿或自定义 AST）。
   - `tools/normalize`：执行字段命名规范、引用路径校正、版本标记等标准化处理。
   - `tools/compose`：将规范化结果与企业扩展合并，生成最终的企业级 schema 库。

3. **成果发布结构**
   - `dist/json/`：面向下游系统的 JSON Schema 文件。
   - `dist/yaml/`：保留 YAML 表达形式，供支持 YAML 的服务使用。
   - `dist/docs/`：自动化生成的 schema 说明文档。

### 4.2 关键能力建设
- **YAML 解析与转换**：利用 `js-yaml` 或 `yaml` 库读取官方文件，结合现有 JSON Schema 验证器生成 Draft-07/2019-09 兼容文件；新增的 `tools/pipeline/build_schemas.py` 原型已验证 Python 方案的可行性，可与 Node.js 生态互补。
- **差异比对机制**：实现原始 JSON 与 YAML 转换结果的结构对比，确保兼容性。
- **扩展元数据支持**：为每个 schema 增加企业级元信息（如数据域、保密级别、主数据映射、参考来源）。
- **自动化验证**：增强 `validate` 脚本，支持对生成成果进行 lint、引用完整性、示例实例校验。
- **版本与发布策略**：制定语义化版本号、更新日志和变更说明生成流程。

### 4.3 阶段性里程碑
1. **基线迁移**：完成官方 JSON 与 YAML 的一致性基准测试，输出首版转换脚本。
2. **企业扩展框架**：定义 overrides 数据结构，实现与官方 schema 的可组合机制。
3. **自动化流水线**：建设 CLI/CI 流程，实现“一键更新数据源 -> 校验 -> 发布”。
4. **文档与培训**：生成开发者指南、扩展流程说明及常见问题。

## 5. 后续行动建议

- 编制更详细的技术设计文档，明确中间数据结构与转换规则。
- 引入单元测试与集成测试，保障转换逻辑的稳定性。
- 评估是否需要引入 TypeScript 或 Python 等更适合批处理的技术栈，以提升可维护性。
- 与业务/数据团队沟通元数据字段定义，确保扩展 schema 满足企业治理要求。
